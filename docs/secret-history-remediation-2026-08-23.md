# Issue #12：历史密钥处置与验收方案（仅方案，不执行）

## 当前结论

- 2026-07-18 已在仓库 owner 明确授权下使用 `git filter-repo` 重写相关分支与标签，并强推清理后的历史。
- 2026-08-04 已复核当前 refs、公开 fork 和 GitHub secret alerts，未发现已知旧泄露位置仍可达。
- 因此本轮**不得再次重写历史或 force-push**。重复执行只会再次改变 commit SHA、破坏开放 PR/本地 clone，并不能让已外泄的凭证失效。
- Issue #12 当前唯一未闭环的核心验收是：旧 DeepSeek Key 是否已在供应商后台吊销或轮换。

## 现在应执行的非代码步骤

1. 仓库 owner 登录 DeepSeek 控制台，找到旧凭证并执行吊销或轮换。
2. 在控制台或独立的最小验证环境中确认旧凭证已失效。验证过程不得把完整 Key 写入命令历史、日志、截图、Issue 或仓库文件。
3. 在 Issue #12 仅回复“已吊销”或“已轮换”及日期；不要粘贴 Key、完整截图、账单或账号信息。
4. 确认后关闭 #12。新凭证只通过 `NASDX_API_KEY` 环境变量或本地私密配置提供。
5. 在 GitHub Settings → Security 中确认 Secret scanning、Push protection，以及适用时的 non-provider pattern / validity checks 已开启；设置状态可记录在 #72，不记录任何凭证内容。

## 只有发现新的可达残留时才考虑再次清理历史

再次重写历史必须同时满足：扫描确认存在新的可达明文、凭证已先吊销、owner 再次明确批准、已安排维护窗口并通知所有协作者。建议步骤：

1. 冻结 push 与合并，记录所有远端分支、标签、开放 PR 和保护规则。
2. 在受控位置创建只读镜像备份或 bundle，并验证可列出全部 refs；备份不得暴露给无关人员。
3. 在独立 mirror clone 中用精确 replace 规则运行 `git filter-repo`，不得在日常工作区试跑。
4. 对重写后的所有分支和标签扫描目标模式，并抽查关键功能提交仍可达。
5. 向 owner 提交“将被改写的 refs、旧新 tip、验证结果、维护窗口和回滚点”，取得明确批准后再协调 force-push。
6. 重建/关闭失效 PR，要求协作者重新 clone 或按新历史迁移；恢复 Ruleset 与 push protection。

## 风险

- 所有受影响提交 SHA 会变化，旧链接、签名提交和签名标签可能失效。
- 现有 clone、fork、开放 PR 和自动化分支可能重新把旧历史推回远端。
- 未充分协调的 force-push 会丢失新提交或让 CI、发布记录无法追溯。
- 历史清理只降低仓库中的暴露面；它不能撤回已复制的 Key，因此供应商侧吊销始终优先。

## 回滚方案

- 维护前保存受保护的 mirror/bundle 和完整 refs 清单；仅在发生仓库完整性事故时使用。
- 需要回滚时冻结写入，在维护窗口从已验证备份恢复指定 refs，并通知全部协作者重新同步。
- 回滚旧 refs 也会重新暴露已清理内容，所以凭证必须保持吊销；若无完整性事故，不应为了恢复旧 SHA 而回滚安全清理。

## 本 Goal 的边界

本文件只提供方案。本 Goal 不执行供应商控制台操作，不读取或验证真实 Key，不运行 filter-repo/BFG，不 force-push，也不修改 master 历史。
